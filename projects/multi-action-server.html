The Multi Action Server Communication Issue

ROS2Action ServersConcurrencyDebugging

The Problem

Our manipulation pipeline orchestrates multiple sequential and parallel actions — move to pre-grasp, open gripper, execute approach, close gripper, retract. Each step is an action server call. Under certain timing conditions, the system would silently fail: an action would complete successfully but the next step would never execute. No errors, no timeouts — just a robot frozen mid-task.

The Investigation

  • Traced the issue to a race condition in how ROS2 action clients handle goal state transitions when multiple action servers are chained
  • The result callback from one action was being processed in a callback group that blocked the goal request of the next action
  • The problem was intermittent — it depended on executor thread scheduling and DDS message ordering
  • Standard ROS2 logging showed clean success states, making the failure invisible without deep introspection

The Fix

  • Restructured the callback group architecture — separated action result processing from goal submission into isolated reentrant callback groups
  • Implemented explicit state machine transitions between action steps with timeout guards
  • Added detailed diagnostic logging at the executor level to catch future callback scheduling issues
  • Contributed findings back to internal documentation for the team

Lesson

ROS2's action server API is powerful but its concurrency model has sharp edges. When you chain multiple action calls in a manipulation pipeline, the interaction between callback groups, executors, and DDS delivery order can create failure modes that don't show up in unit tests or simulation — only on real hardware under real timing constraints.
